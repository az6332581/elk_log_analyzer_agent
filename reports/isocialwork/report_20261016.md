## 🌐 1. 全域連鎖因果與相互影響分析 (Correlation & Root Cause)

經全域因果分析，本次異常呈現明顯的『基礎設施連鎖失效』特徵。根本原因（Root Cause）並非單一程式碼邏輯錯誤，而是底層網路服務發現（Service Discovery）失效導致的連鎖反應：
1. **核心網路故障**：錯誤 ID 3, 4, 5, 12 均指向 `php_network_getaddresses: getaddrinfo failed`。這顯示容器網路或 DNS 解析無法識別 `isocialwork_redis` 與 `isocialwork_mysql` 這兩個 Hostname。這導致了 Redis 連線失敗（ID 3, 4）與 MySQL 連線失敗（ID 5, 12）。
2. **連鎖效應 (Cascading Failure)**：由於資料庫與快取無法連線，系統在嘗試進行權限檢查（Permissions）與警報查詢（sw_s_alert）時發生阻塞或異常拋出，進而引發了大量的 `QueryException`。
3. **效能退化 (Performance Degradation)**：錯誤 ID 6-11 顯示極端嚴重的 Slow Query（最高達 10s 以上）。這極有可能是因為網路解析超時（DNS Timeout）或在連線失敗邊緣進行重試（Retry Mechanism）所導致的請求堆積，而非單純的 SQL 索引問題。
4. **安全性風險**：ID 2 的 AES 解密失敗可能與資料庫連線中斷導致無法讀取正確的加密金鑰（Key/IV）或配置有關，屬於連鎖失效後的次生問題。

## 🛠️ 2. 跨檔案協同修復計畫 (Coordinated Multi-File Fix Plan)

修復策略必須採取『基礎設施優先，程式碼容錯為輔』的雙軌制。首先必須解決 DNS 解析問題，隨後在程式碼層級強化對基礎設施不穩定時的『斷路器（Circuit Breaker）』機制，避免連鎖超時。

### 📋 協同修復與驗證清單 (Checklist)
- [ ] 1. 基礎設施修復 (Infrastructure Layer)：檢查 Docker Compose 或 Kubernetes Service 定義，確保 `isocialwork_redis` 與 `isocialwork_mysql` 服務名稱正確且處於 Running 狀態；重啟容器網路插件以修復 DNS 解析失效問題。
- [ ] 2. 配置與連線優化 (Config Layer)：檢查 `.env` 或 `config/database.php`，確認 Hostname 是否與服務發現名稱一致；針對 `isocialwork_mysql` 增加 `options => [PDO::ATTR_TIMEOUT => 5]` 以防止無窮等待導致的 Slow Query。
- [ ] 3. 程式碼容錯強化 (Application Layer)：在 `Permissions` 權限載入邏輯（對應 ID 4, 5）中加入 `try-catch` 區塊，當 Redis/DB 無法連線時，應回退（Fallback）至預設權限或緩存，而非直接拋出致命錯誤導致整個請求崩潰。
- [ ] 4. 加密邏輯校驗 (Security Layer)：檢查 AES 解密模組，確保在資料庫連線異常時，不會因讀取不到加密 Salt 而導致解密失敗，並增加對解密失敗的日誌分級（從 Error 降級為 Warning，避免日誌爆炸）。
- [ ] 5. 執行全量測試驗證：執行整合測試（Integration Tests）模擬網路延遲與服務不可用情境，驗證系統是否能正確觸發 Fallback 機制並通過全量測試。
