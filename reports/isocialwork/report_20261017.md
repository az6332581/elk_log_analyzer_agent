## 🌐 1. 全域連鎖因果與相互影響分析 (Correlation & Root Cause)

經分析，系統目前面臨兩大核心問題的連鎖效應：1. 【資料庫效能瓶頸】：大量 Slow query (最高達 8539ms) 顯示資料庫層級存在嚴重的索引缺失或全表掃描問題，這會導致應用層 Thread Pool 耗盡，進而引發連鎖性的請求堆積與超時。2. 【加密解密邏輯失效】：AES Decryption Failed (ID: 10) 發生 6 次，這通常與金鑰管理 (Key Management) 或加密模式 (CBC/ECB) 的遷移不一致有關。若解密失敗導致資料無法正確讀取，可能會觸發異常的重試機制或錯誤的資料庫查詢邏輯，進一步加劇 Slow query 的發生。兩者共同作用，極可能導致系統在處理敏感加密資料時，因解密失敗後的錯誤處理路徑（Error Path）觸發了低效的資料庫查詢，形成惡性循環。

## 🛠️ 2. 跨檔案協同修復計畫 (Coordinated Multi-File Fix Plan)

修復策略應採取『先穩定資料存取，再修復加密邏輯』的順序。首先透過優化資料庫索引與查詢邏輯來降低延遲，釋放系統資源；接著修復 AES 解密模組，確保加密金鑰與模式的向下相容性。具體建議：針對 Slow query，需定位出錯的 SQL 並建立對應的 B-Tree 索引；針對 AES 錯誤，需檢查解密函式中是否正確處理了 Legacy ECB 模式的 Padding 與 IV 參數。

### 📋 協同修復與驗證清單 (Checklist)
- [ ] 1. 優化資料庫存取層 (Database Access Layer)：針對 Slow query 頻發的 Table，執行 `CREATE INDEX` 指令，並檢查 ORM 查詢是否包含未經索引的 `WHERE` 條件或過大的 `JOIN` 操作。
- [ ] 2. 修復加密模組 (Security/Crypto Utility)：檢查 `isocialwork` 專案中負責 AES 解密的 Class，確保在嘗試 CBC 失敗後，切換至 ECB 模式時能正確處理 `PKCS7` Padding，並確認金鑰來源 (Environment Variable/KMS) 的一致性。
- [ ] 3. 實施連鎖壓力測試：在修復後，模擬高併發加密讀取場景，觀察 Slow query 是否因解密成功後的正常路徑而下降，並確認 AES 錯誤率歸零。
- [ ] 4. 執行全量 pytest 測試驗證協同修復成果，特別是針對 `test_decryption_compatibility` 與 `test_database_performance_threshold` 測試案例。
