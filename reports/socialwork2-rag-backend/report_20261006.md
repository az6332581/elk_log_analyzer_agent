## 🌐 1. 全域連鎖因果與相互影響分析 (Correlation & Root Cause)

經分析，系統正經歷一場由『基礎設施不穩定』引發的『連鎖失效 (Cascading Failure)』。根本原因（Root Cause）在於資料庫層級：1. PostgreSQL 發生異常重啟或崩潰（Error 7: database system is in recovery mode），導致大量連線中斷（Error 6 & 8: server closed the connection unexpectedly）。2. 當資料庫恢復時，由於 RAG 檢索邏輯（Error 3）與 LLM 請求（Error 1, 4, 5）在壓力下同時湧入，導致網路與資源競爭加劇。3. LLM 端出現 Timeout (240s) 與 Connection Failed，顯示 NCHC API 或內部網路在資料庫恢復期間承受了極大負載。4. 最終導致業務邏輯層面的數據一致性問題（Error 2: Pydantic validation failed），這是因為 LLM 在不穩定的網路環境下，可能回傳了格式不完整或包含重複 slug 的錯誤 JSON 結構，導致下游 Pydantic 模型解析失敗。總結：DB 崩潰 -> 檢索失敗 -> LLM 請求重試/超時 -> LLM 回傳髒數據 -> Pydantic 驗證失敗。

## 🛠️ 2. 跨檔案協同修復計畫 (Coordinated Multi-File Fix Plan)

修復策略必須採取『防禦性編程』與『斷路器機制』。首先，必須強化資料庫連線池的穩定性與重試機制；其次，在 LLM Client 層引入更嚴謹的 Timeout 管理與 JSON 完整性檢查；最後，在 Schema 層容忍微小的重複數據或在 LLM 輸出端進行 Pre-processing。具體改動如下：

1. **Database Layer**: 在 SQLAlchemy Engine 配置中加入 `pool_pre_ping=True` 以自動檢測失效連線，並在 `connection_async.py` 實作指數退避 (Exponential Backoff) 重試邏輯，避免在 DB Recovery 期間造成連線風暴。
2. **LLM Client Layer**: 修改 `llm_client.py`，將 `timeout` 參數與 `max_network_attempts` 結合，並在第 154 行後的 `finish_reason == 'length'` 邏輯中，增加對 JSON 完整性的強制檢查，若不完整則直接拋出 `LLMError` 而非交給下游解析。
3. **Schema Layer**: 修改 `SfaaVisitRecord` 的 Pydantic 定義，針對 `treatment_issues` 使用 `Set` 或在 `field_validator` 中加入 `set()` 去重邏輯，以容忍 LLM 可能產生的重複 slug 錯誤。
