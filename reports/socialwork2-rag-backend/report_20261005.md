## 🌐 1. 全域連鎖因果與相互影響分析 (Correlation & Root Cause)

經分析，系統正遭受『基礎設施不穩定』與『LLM 服務壓力』的雙重打擊，並形成連鎖失效。根本原因可歸納為三層：1. 基礎設施層 (Infrastructure Layer)：PostgreSQL 發生連線中斷與 Recovery Mode (Error 6, 7, 8)，這直接導致 RAG 檢索階段 (Category_Planned_Retrieval_Failed) 大規模失敗，影響系統可用性。2. 模型服務層 (Model Service Layer)：NCHC LLM API 遭遇 429 Rate Limit (Error 9) 與 504 Timeout (Error 1, 4, 5)，顯示當檢索壓力或請求量增加時，LLM 供應商無法負荷。3. 應用邏輯層 (Application Logic Layer)：由於 LLM 回傳內容可能因 max_tokens 限制被截斷 (Error 152-156 註解提及)，導致 Pydantic 在解析 JSON 時出現重複 slug 或格式錯誤 (Error 2)，這是一種典型的『因模型輸出不完整導致的 Schema 驗證崩潰』。連鎖反應路徑為：DB 不穩 -> 檢索失敗 -> 請求重試/堆積 -> LLM API 壓力過大/超時 -> LLM 回傳截斷 JSON -> Pydantic 驗證失敗。

---

## 🛠️ 2. 跨檔案協同修復計畫 (Coordinated Multi-File Fix Plan)

修復策略必須從『增強容錯』與『流量控制』雙管齊下。首先，必須在 LLM Client 層實作針對 429 錯誤的指數退避 (Exponential Backoff) 重試機制，而非僅僅拋出錯誤；其次，針對 Pydantic 驗證失敗，應在解析前檢查 finish_reason，若為 'length' 則應拋出特定的『內容不完整』異常而非讓其進入 Schema 驗證；最後，必須優化資料庫連線池配置，以應對 Recovery Mode 期間的連線震盪。

### 📋 協同修復與驗證清單 (Checklist)
- [ ] 1. 修復 llm_client.py: 在第 130-135 行的異常處理中，增加對 status_code == 429 的判斷，並實作包含 jitter 的指數退避重試邏輯，避免直接拋出 LLMError 導致業務中斷。
- [ ] 2. 修復 llm_client.py: 在第 154 行後的邏輯中，若 `choice.get("finish_reason") == "length"`，應主動拋出 `IncompleteJSONError`，防止下游 Pydantic 嘗試解析殘缺 JSON 導致無意義的 Schema Validation Error (Error 2)。
- [ ] 3. 修復 Pydantic Models (SfaaVisitRecord): 在 `treatment_issues` 的 validator 中增加 `set()` 去重邏輯，確保即使 LLM 產生重複 slug，系統仍能以『容錯模式』運作而非直接崩潰。
- [ ] 4. 優化 SQLAlchemy 配置: 在資料庫連線模組中增加 `pool_pre_ping=True` 與更激進的 `pool_recycle` 設定，以應對 PostgreSQL 伺服器異常關閉連線 (Error 6) 的情況。
- [ ] 5. 執行全量 pytest 測試驗證協同修復成果，特別需包含 Mock LLM 429/504 狀態碼與 Mock Truncated JSON 的集成測試。
